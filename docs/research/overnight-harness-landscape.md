# Overnight coding-agent harness landscape

Research checked 2026-09-22. This is a source-backed feature comparison and a prioritized experiment list for pk's long-running Luna tasks. It does not rank model quality. Vendor docs describe product behavior; open repositories let us inspect implementation; neither by itself proves a task-success or efficiency advantage.

## Projects verified

| Project | What is verified | Evidence boundary |
|---|---|---|
| [OpenCode V2](https://opencode.ai/v2/docs) | The official V2 docs describe mouse capture, configurable paste/editor context, replay limits, model/context/usage footer, structured questions and permission prompts, and checkpoint-based auto-compaction. The V2 compactor retains a configurable recent tail (default 15,000 tokens), reserves headroom, checkpoints at safe step boundaries, and keeps the prior transcript on disk. | These links describe OpenCode's V2 docs/product contract. Defaults and behavior can vary by provider/model. They are not evidence V2 has higher task success. |
| [Grok Build](https://github.com/xai-org/grok-build) | xAI announced its coding-agent harness and TUI source as open source. The official repo describes a fullscreen mouse-interactive TUI, headless use and ACP; source prompt template describes background commands and monitoring. Its compaction crate sets an 85% default trigger and retries transient summary failures. | The source is inspectable; the 85% threshold is a vendor default, not a universal optimum. Grok Build has also imported code from other projects; use its implementation as a reference, not attribution for copied components. |
| [OpenAI Codex](https://github.com/openai/codex) | The official CLI and app-server source is public. Its event protocol has turn/item lifecycle events, final usage, and an explicit request/response for user input; approval requests are separately typed. | App-server user-input support is marked experimental in its protocol docs. Confirm the actual client/CLI surface before promising a particular interaction. |
| [Hermes Agent](https://github.com/NousResearch/hermes-agent) | Nous Research publishes the agent and source. Its CLI docs cover multiline editing, interrupt-and-redirect, streaming tools, session resume/worktrees, and a live model/context/cost/time status bar. The tool gateway uses request/response methods for clarification and approvals. It also publishes a Terminal-Bench 2.0 evaluation environment with per-task test verification. | Product descriptions such as “self-improving” are vendor claims; the table records inspectable features, not evidence they improve coding outcomes. The CLI is one surface among several terminal backends. |
| [DeepSeek Harness (`dsh`)](https://github.com/deepseek-ai/deepseek-harness) | Verified identity: DeepSeek's official harness repository, currently marked developer preview. Official docs describe composable plugins for models, tools, sessions, sandboxes, storage, loops, scheduling, and UI. Its user-question API uses stable question IDs, structured choices/free text, an abort signal, and a typed failure contract; approval is a separate seam. | Do not confuse this with DeepSeek Coder, a community TUI, or third-party “DeepSeek harness” projects. | [Claude Code](https://github.com/anthropics/claude-code) | Anthropic's official docs describe interactive permission modes, session-persistent approvals, hooks including `Stop`, `PostCompact`, and `PermissionRequest`, local session resume, compaction, and different behavior in noninteractive `-p` mode. The public official repository contains docs/plugins/issues; it does not publish the CLI implementation. | Treat this as documented product behavior, not source-audited internals. Do not use leaked source maps, mirrors, or unofficial “source” repositories as authoritative implementation evidence. |

## Implementable lessons for pk

1. **Make the context budget visible and compaction recoverable.** Keep the full append-only transcript, but build a bounded model view: estimate prompt size before each request, compact at a measured safety threshold, keep a configurable recent tail, and retry the same pending model step after a successful checkpoint. Persist checkpoint completion before advancing queued user input; make manual compaction idempotent with a request ID. OpenCode V2 documents these behaviors and defaults; Grok Build's 85% trigger is a useful test point, not a value to copy blindly. Preserve pk's stable session/cache key and invariant system/tool prefix across compaction and resume; test cache-hit usage instead of assuming the cached prefix survived.

2. **Put hard bounds around unattended loops.** A detached run needs maximum steps, per-command and total wall-clock limits, child-process cancellation/reaping, and a terminal outcome that distinguishes success, failure, cancellation, and interruption. Add a cheap repeated-output/tool-call detector and a last-progress timestamp so low-entropy or stalled workers become a visible failure rather than consuming the entire budget. Emit heartbeat events with current stage, last completed tool, elapsed time, and next intended check. Use a verifier or test result as the completion condition; do not use “assistant stopped speaking” alone. Grok Build documents detached background-command monitoring and reminders; Hermes' evaluation environment exposes a maximum agent-turn setting. These are guardrails, not proof against every model loop.

3. **Add structured foreground questions and confirmations as separate protocols.** A clarification should state the finding, why pk is blocked, consequence of each choice, and a recommendation where useful. Give each request/question a stable ID, explicit choices plus free text, and explicit answer/decline/cancel outcomes. Tool permission approval should show the exact action, working directory, and scope of any “always allow” choice. Persist a pending request before displaying it and clear it on cancel or terminal transition. Codex and DeepSeek Harness use structured request/response lifecycles; OpenCode and Hermes keep questions distinct from execution approval. Do not expose a blocking ask tool to detached workers until pk has a durable `awaiting_input` state and reconnectable reply path. OpenCode's official issue tracker records a headless question hang when that boundary was missed.

4. **Treat the TUI as a bounded control surface.** Keep mouse support optional and preserve keyboard-first operation. Use compact paste previews, an editable multiline composer, resumable event/history view with a replay cap, and a persistent footer for model, elapsed time, tokens/context, cache usage, and task status. Tool output should show a short excerpt plus a way to inspect the complete persisted artifact. Limit in-memory transcript/render buffers independently of durable storage. OpenCode V2 and Hermes document these interaction/status affordances; Claude's docs call out mouse capture as a real terminal behavior that needs explicit copy/scroll handling.

5. **Evaluate Luna as part of the harness, not as a chat model in isolation.** Pin model snapshot/route, reasoning effort, prompts, tools, permissions, task workspace, resource limits, and cache policy. Use small deterministic adapter fixtures for lifecycle/cache/compaction regressions, then run a separate live suite with isolated fresh workspaces and repeated tasks in interleaved A/B order. Score repo state with tests or a verifier and inspect traces for forbidden actions, lost tool results, duplicate work, timeout/cancel behavior, and unsupported completion claims. Report per-task success, cost including cache reads, p50/p95 duration, tool/turn counts, and failures; retain raw transcripts and configs for replay. Hermes shows task-level Terminal-Bench verification; the pk [evaluation plan](evaluation-plan.md) already specifies paired controls, repeats, and trace review. No official OpenCode, Grok Build, Codex, or DeepSeek Harness source examined here establishes a cross-harness winner.

## Benchmark-method caveats

DeepSeek Harness is explicitly in developer preview and its repo's `BENCHMARK.md` is a short run instruction, not a published agent-quality comparison. Hermes contains an evaluation environment for Terminal-Bench 2.0, which verifies each task in its Docker image; that is more useful for correctness than self-reported completion but still says nothing about Luna unless Luna is the evaluated model. Grok Build and Codex publish source and tests, not a comparable harness leaderboard in the sources reviewed here. Claude Code docs describe workflows and controls, not a reproducible proprietary CLI benchmark. Public benchmark numbers should therefore be treated as different products/tasks/configurations unless the fixture, model, permissions, budgets, verifier, and trials are matched.
