# Provider preset research

Research checked 23 September 2026 against current provider documentation and the local provider adapter at baseline commit `033bf40`. This is a compatibility map, not a ranking or an endorsement. Provider protocol support, model availability, and model names change; verify against the linked docs when updating presets. Changes after that baseline, including the in-progress native Anthropic adapter, may alter the local capability statements below.

## Adapter baseline at `033bf40`

`internal/providers` accepts exactly two explicitly selected wire protocols: OpenAI Responses (`POST {base}/responses`) and OpenAI Chat Completions (`POST {base}/chat/completions`). Both use `Authorization: Bearer …`. Model discovery makes an authenticated `GET {base}/models` and expects the OpenAI list shape `{ "data": [{ "id": "…" }] }`. The adapter does not currently accept provider-specific headers, query-key authentication, provider-specific model-list paths, or native Anthropic/Google request formats. Do not infer support from a provider name or from the existence of an OpenAI-compatible endpoint.

For first-pass guided presets, OpenAI, Gemini, OpenRouter, Groq, Together, xAI, Cerebras, and Mistral have useful Chat or Responses compatibility evidence. Fireworks can be manually configured for inference but needs a model-catalog adapter for first-class discovery. Anthropic requires a separate native adapter. Treat these as preset candidates, not a guarantee every selected model supports tools, images, reasoning effort, or every request field pk sends.

## Model lists are not one thing

There are two distinct sources of model information:

1. **Provider-authenticated discovery** asks the selected endpoint for models using the user's configured key. It is the best source for the current key's visible IDs when that provider exposes a compatible endpoint. The response may still list models unavailable for inference, omit deployment-specific models, require account identifiers, or use a provider-specific schema. Treat a `GET /models` failure as discovery unavailable; do not silently substitute another provider or claim the model is usable.
2. **A static/curated catalog** such as [Models.dev](https://models.dev/) is useful for preset labels, model descriptions, modalities, and maintained provider metadata. OpenCode's provider code uses Models.dev, and its project documents the catalog as community-maintained model/provider specifications at [`https://models.dev/api.json`](https://models.dev/api.json). It is not a universal endpoint contract or proof of account entitlement. OpenCode's custom-provider docs separately require the configured base URL and model entries, reinforcing that catalog metadata and a provider's live endpoint are different layers. [OpenCode provider implementation](https://github.com/anomalyco/opencode/blob/dev/packages/opencode/src/provider/provider.ts), [Models.dev README](https://github.com/anomalyco/models.dev/blob/dev/README.md), [OpenCode custom providers](https://github.com/anomalyco/opencode/blob/dev/packages/web/src/content/docs/providers.mdx)

Recommended UX: presets supply verified base URL, protocol choice, and conventional environment variable name; then query that provider's own supported model-list endpoint where compatible. Keep free-form model ID entry for private deployments and incomplete list APIs. Do not use a static catalog as a fallback that looks like authenticated discovery.

## Implementation notes

- Keep custom base URLs and explicit protocol selection. Providers often offer multiple APIs and an OpenAI-compatible label does not imply identical semantics.
- Avoid global reasoning-effort flags. Capability varies by model and sometimes by protocol; current pk config's provider-wide boolean can otherwise send unsupported fields.
- Avoid choosing volatile model IDs as preset defaults. If a default is necessary, annotate its source/date and allow `/models` to reveal that the selected account cannot access it.
- Add provider-specific `models` URL/schema overrides before adding providers whose documented discovery contract is not OpenAI-shaped (notably Fireworks). Never guess an account ID or scrape a catalog endpoint.
- A provider-specific native adapter is needed for Anthropic Messages and for native Gemini features outside Google's compatibility layer. A provider preset should not imply those feature sets are implemented.
