# Go runtime research for pk

## Recommendation

Proceed with Go for the first harness runtime, while keeping provider, tool, event, and plugin boundaries language-neutral. Go fits a process-and-I/O-heavy coordinator: goroutines are lightweight, `context.Context` carries cancellation/deadlines, and the standard library includes HTTP and child-process primitives. Rust offers tighter memory/CPU control and avoids a tracing garbage collector, but those advantages matter most if profiling shows the coordinator itself is a material bottleneck or if the product grows an embedded inference/kernel component. Go's own guidance cautions that more concurrency can add synchronization cost rather than speed up sequential work ([Effective Go](https://go.dev/doc/effective_go), [Go FAQ](https://go.dev/doc/faq)); treat the language choice as an implementation/productivity tradeoff, not a speed claim.

The model's inference time is usually in a remote provider or a local inference server/runtime. A language rewrite cannot materially reduce that work. The harness can affect startup, request setup, tool launch, serialization, buffering, persistence, and scheduling. Measure those separately from provider time-to-first-event and generation time. Rust's ownership system can provide memory-safety guarantees without a garbage collector ([Rust Book](https://doc.rust-lang.org/book/ch04-00-understanding-ownership.html)); that is a real benefit for tight memory bounds, but it does not make HTTP, subprocess, disk, or model inference intrinsically faster.

## Suggested Go runtime shape

Use a small coordinator with explicit state transitions and a bounded amount of work at every boundary:

1. **Run supervisor.** One run owns a root context, deadline, cancellation cause, event sequence, and child registry. Each tool/provider call gets a child context. On cancel or timeout, stop accepting work, cancel children, close stdin and pipes, terminate children, wait/reap them, then persist a terminal event. `exec.CommandContext` kills the direct child by default when its context ends; wrap platform-specific process-group/job-object behavior behind a supervisor if tools may create descendants. The Go `os/exec` package does not invoke a shell implicitly, which is a useful safe default ([os/exec docs](https://pkg.go.dev/os/exec), [context design](https://go.dev/blog/context)).

2. **Bounded event path.** Represent provider deltas, tool starts/results, approvals, cancellations, and run status as typed append-only events with run ID, monotonic sequence, timestamp, and payload. A bounded channel between producers and the event writer provides backpressure: when persistence or a client is slow, the producer waits or the run applies an explicit policy. Do not spawn a goroutine per event or use an unbounded queue. Separate lossless durable events from optional/coalescible UI telemetry; never silently drop tool results or terminal state. Go buffered channels block when full, and Tokio's bounded MPSC is the comparable Rust pattern ([Effective Go channels](https://go.dev/doc/effective_go#channels), [Tokio bounded channel](https://docs.rs/tokio/latest/tokio/sync/mpsc/fn.channel.html)).

3. **Event store.** Start with newline-framed JSONL for inspectable early prototypes if single-writer durability/query needs are modest; otherwise use SQLite behind a narrow `EventStore` interface. A single writer goroutine batches inserts into transactions; readers query by `(run_id, sequence)`. SQLite WAL lets readers proceed alongside a writer, but SQLite still serializes writers and WAL assumes same-host filesystems ([SQLite WAL](https://www.sqlite.org/wal.html)). For Go SQL access, the standard `database/sql` API provides context-aware operations and transactions ([Go database docs](https://go.dev/doc/database/), [transactions](https://go.dev/doc/database/execute-transactions)). Select a driver only after validating portability, CGO policy, backup/recovery, and write throughput; no driver is prescribed here.

4. **Provider streaming.** Define a provider interface returning a stream of normalized semantic events, with provider-specific request/response types isolated behind adapters. Use `net/http` first unless a chosen provider SDK clearly removes substantial maintenance work. Parse SSE incrementally and emit typed deltas; keep the upstream response body open only while the consumer can accept data. The Responses API documents streamed output as typed server-sent events and explains that streaming lets processing begin before generation completes ([OpenAI streaming guide](https://developers.openai.com/api/docs/guides/streaming-responses), [event reference](https://platform.openai.com/docs/api-reference/responses-streaming)). Bound buffers and propagate run cancellation through the HTTP request context. Do not persist each token synchronously; batch/coalesce display deltas while preserving ordering and final content.

5. **Tools and plugins.** Run ordinary tools as child processes with argument arrays, explicit environment, working directory, timeouts, output caps, and a protocol over stdin/stdout (reserve stderr for diagnostics). Drain stdout and stderr concurrently to avoid pipe deadlocks; call `Wait` only after pipe reads finish, per `os/exec` contract. Treat child-process isolation as a reliability boundary, not a complete security sandbox: OS permissions still determine access. For third-party in-process extensions, prefer a capability-limited WASM interface only when plugin demand exists. `wazero` is a Go-native WebAssembly runtime with no CGO requirement and configurable host/module boundaries ([wazero project](https://github.com/tetratelabs/wazero)); it should not be added before a concrete plugin ABI exists.

6. **Resource controls and metrics.** Add global and per-run limits for concurrent tool processes, provider calls, queued bytes/events, event-store batch size, and output size. Expose harness-side counters/timings: active runs and subprocesses, queue depth/blocked time, process start-to-ready and exit time, provider request/first-event/complete durations, bytes streamed, event commit latency, and cancellation-to-reap latency. Sample Go runtime metrics (heap classes, GC CPU, goroutines, scheduler state) via `runtime/metrics`; use `pprof` to locate CPU/allocation costs rather than optimizing by intuition ([runtime/metrics](https://pkg.go.dev/runtime/metrics), [Go diagnostics](https://go.dev/doc/diagnostics)). Runtime metrics describe the Go process, not total machine or child-process resource usage. Add optional OS-specific child/process sampling behind small adapters; Linux `getrusage` provides process CPU and resource counters ([getrusage](https://man7.org/linux/man-pages/man2/getrusage.2.html)). Keep sampling low frequency and label unavailable metrics rather than implying cross-platform equivalence.

## Go versus Rust for this harness

| Concern | Go implication | Rust implication |
|---|---|---|
| Process/HTTP orchestration | Standard library covers HTTP, contexts, and subprocesses; simple concurrency model suits many independent I/O tasks. | Strong systems control and async ecosystem; Tokio has bounded channels with backpressure and child-process APIs including kill-on-drop ([Tokio process](https://docs.rs/tokio/latest/tokio/process/struct.Command.html)). |
| Memory behavior | GC simplifies ownership and buffers, but allocations and GC work must be observed under representative streams. | No tracing GC; ownership/lifetimes make resource ownership explicit, with a learning/implementation cost. |
| Isolation | Child processes are straightforward; WASM embedding via wazero is an option. | Child processes and WASM are possible too; language choice does not replace OS-level sandboxing. |
| Performance question | Likely wins by keeping the core lean, avoiding copies, bounding queues, and minimizing persistence overhead. | Consider if controlled measurement finds Go GC/allocation or CPU overhead affects latency, throughput, or memory goals. |

This comparison is an architectural assessment, not a benchmark result. It does not assume pk's model provider, concurrency target, event volume, deployment OS, or local-inference plan.

## Experiments before optimizing

Establish a baseline on each supported OS and report distributions (median and tail percentiles), throughput, peak RSS, CPU time, and allocation/GC data. Record hardware, Go/Rust versions, build flags, provider, concurrency, prompt/output sizes, and persistence mode. Compare identical behavior and use a fake provider/tool for repeatability before testing a real provider.

- **Coordinator floor:** no-op run create/cancel/finish, with and without event persistence; measure run startup/finish latency, allocations, RSS, and events/sec.
- **Stream path:** replay fixed synthetic SSE traces (many small deltas and fewer large chunks) into a slow and fast consumer. Measure first-event-to-render delay, bytes copied, queue high-water mark, blocked producer time, and memory growth. Verify the slow consumer produces bounded memory and cancellation completes promptly.
- **Subprocess lifecycle:** repeatedly launch a no-op child, a child that writes heavily to both stdout/stderr, a child that ignores graceful termination, and a child that starts a descendant. Measure spawn-to-ready, throughput, memory, pipe behavior, timeout/cancel-to-reap, and orphan count. Test OS-specific termination semantics.
- **Persistence:** append representative event sizes at expected and stress rates; compare JSONL and SQLite transaction batching, flush policy, crash recovery, and concurrent reads. Report durability settings and fsync behavior alongside latency.
- **End-to-end decomposition:** use a controlled local/fake model server, then a real provider. Record queue/setup, time-to-first-event, stream duration, tool time, and store time as separate spans. Do not attribute provider/inference latency to Go or Rust.
- **Go/Rust decision gate:** implement only the minimal coordinator path in both languages if early measurements reveal a specific suspected runtime bottleneck. Compare the same tests; keep Go unless Rust improves a user-visible objective enough to justify a second implementation/toolchain and maintenance cost.

No benchmark numbers are asserted here; all are measurements to run against pk's chosen targets and workload.
